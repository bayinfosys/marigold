# Configuration

Marigold reads two files:

| File | Where | What it holds |
|---|---|---|
| `marigold-host.toml` | on the host | how this machine runs the platform: compose files, storage, database, registries, network, resource limits, model settings |
| `marigold.toml` | in each application | what the application is and runs; see [Building](building.md) |

An application config that sets a host section is rejected. Both files
may set `[environment]`; the application's values win per key.

Every setting goes through these two files. The CLI validates
`marigold-host.toml` against one model (`cli/host_config.py`) and hands
the platform's containers the result as environment variables, so no
container reads configuration from anywhere else. The tables below are
generated from that model.

## Where it is read from

First match wins:

1. `--host-config PATH` on the command line
2. `$MARIGOLD_HOST_CONFIG`, which must exist when set
3. `marigold-host.toml` in the current directory
4. `~/.marigold/marigold-host.toml`

With no file, every value is its default. Because of rule 3, changing
directory can change which file is used; set `MARIGOLD_HOST_CONFIG` or
pass `--host-config` in scripts.

```sh
marigold config path          # the marigold-host.toml in use
marigold config show [name]   # every resolved value, marked [host] or [default]
```

## Example

```toml
[platform]
compose_files = ["core", "cpu", "gpu"]

[storage]
location = "/data/marigold"

[[registry]]
url = "https://examples.marigold.run/"
name = "examples"                  # optional

[network]
bind = "0.0.0.0"                   # reachable from other machines

[resources.worker]
memory = "48g"                     # below the host's total memory
```

## Sections

Unknown sections and keys are errors.

### `[platform]`

| Key | Default | Description |
|---|---|---|
| `compose_files` | `["core", "cpu"]` | Platform compose files. Add "gpu" for an NVIDIA worker: ["core", "cpu", "gpu"]. |
| `tag` | unset | Image tag for the platform images. Unset means the installed CLI's version. |
| `log_level` | `"INFO"` | Log level for the worker and application instances. |
| `idle_timeout` | `120` | Seconds the worker keeps a model loaded with an empty queue. 0 never unloads. |

### `[storage]`

| Key | Default | Description |
|---|---|---|
| `location` | `"~/.marigold/cache"` | The cache directory: models, the platform database, outputs and installed applications. A local path or a mounted network share. |
| `outputs` | `"fs"` | Where images, audio and video outputs are stored: files under the cache, S3, or Azure Blob Storage. |
| `bucket` | unset | s3: the bucket, which must already exist. |
| `endpoint` | unset | s3: the endpoint of an S3-compatible service. Unset means AWS S3. |
| `region` | unset | s3: the region, passed as AWS_DEFAULT_REGION. Unset leaves the shell's AWS_DEFAULT_REGION. |
| `container` | unset | azure: the blob container, which must already exist. |

### `[database]`

| Key | Default | Description |
|---|---|---|
| `url` | unset | An external Postgres connection string. Unset means the platform's own Postgres, built from the keys below. |
| `name` | `"marigold"` | Platform Postgres: database name. |
| `user` | `"marigold"` | Platform Postgres: user. |
| `password` | `"marigold"` | Platform Postgres: password. |

### `[[registry]]`

Registries searched for applications, in file order. The first registry listing a name supplies it.

| Key | Default | Description |
|---|---|---|
| `url` | required | The registry's address: http:// or https://. |
| `name` | unset | A local name for the registry, as with git remotes. Recorded only; nothing resolves by it yet. |

Default: none.

### `[network]`

| Key | Default | Description |
|---|---|---|
| `bind` | `"127.0.0.1"` | Host address the API and Open WebUI publish on. "0.0.0.0" publishes on every interface, so other machines can reach them. |
| `api_port` | `8000` | Host port for the API. |
| `webui_port` | `3000` | Host port for Open WebUI, when an application adds it. |

### `[resources]`

#### `[resources.executor]`

Each application instance.

| Key | Default | Description |
|---|---|---|
| `memory` | `"4g"` | Memory limit, such as '4g'. Unset means no limit. |
| `cpus` | `2.0` | CPU limit, in cores. Unset means no limit. |
| `pids` | `512` | Process and thread limit. Unset means no limit. |

#### `[resources.worker]`

| Key | Default | Description |
|---|---|---|

| `cpus` | unset | CPU limit, in cores. Unset means no limit. |
| `pids` | unset | Process and thread limit. Unset means no limit. |
| `shm` | `"2g"` | Shared memory (/dev/shm) for the worker, used by PyTorch. |

| `cpus` | unset | CPU limit, in cores. Unset means no limit. |
| `pids` | unset | Process and thread limit. Unset means no limit. |

#### `[resources.postgres]`

The platform Postgres.

### `[models]`

| Key | Default | Description |
|---|---|---|
| `load_in_4bit` | unset | Quantise the weights to 4-bit as they load (bitsandbytes). Needs a GPU. |
| `use_fast` | unset | Load the fast tokenizer. |
| `trust_remote_code` | unset | Run Python code from the model's repository during the load. |
| `low_cpu_mem_usage` | unset | Load the weights without a full copy in host memory. |
| `types` | `{}` | Settings for every model of one type, as [models.types.<type>]. |
| `names` | `{}` | Settings for one model, as [models.names."<name>"], the name as models.yaml writes it. |

### `[environment]`

Compose variables. A service receives one where its compose file names it. An application's [environment] wins per key. Neither file may set a variable the platform sets from another section.

Default: none.

## Model settings

A model's settings decide how it loads and runs: 4-bit quantisation,
the tokenizer, remote code, and the values a handler reads, such as
`num_steps`. A setting's name is lower-case letters, digits and
underscores. An application declares settings per model under `settings:` in
its models.yaml; every setting each loader and handler reads is listed
in [Building](building.md#model-settings).

`[models]` sets them on the host. Settings that depend on the hardware,
such as quantisation, belong here, and the application stays unchanged:

```toml
[models]
load_in_4bit = true                 # every model: two 12 GB cards

[models.types.txt2img]
load_in_4bit = false                # except image generation

[models.names."qwen/qwen3-8b"]
trust_remote_code = false           # and refused for this model
```

At each load the worker resolves every setting from five levels, each
overriding the one before:

1. the loader's default
2. the application's models.yaml
3. `[models]`
4. `[models.types.<type>]`
5. `[models.names."<name>"]`, the name as models.yaml writes it

The host takes precedence over the application, so a host can refuse
`trust_remote_code` for every application. The worker logs the result
as one line per load, each value with its source:

```
settings for 'qwen/qwen3-8b': load_in_4bit=true (host) low_cpu_mem_usage=true (default) trust_remote_code=false (host name) use_fast=false (default)
```

A setting applies to the model it resolves for and to no other. On a
worker with no CUDA device, `load_in_4bit` fails the load with a
message saying 4-bit needs a GPU, and the model is marked failed.

`marigold cache populate` downloads with the same settings, with
`load_in_4bit` off: quantisation happens as weights reach a GPU, and
the download needs none.

The CLI passes `[models]` to the worker and the cache container as
`MARIGOLD_MODEL_SETTINGS`. A compose run without the CLI carries no
host settings, and each model loads with its application's settings.

## Secrets

Credentials never go in `marigold-host.toml`. The CLI passes these
from the shell environment to the containers that need them:

| Variable | Used for |
|---|---|
| `HF_TOKEN` | gated or private Hugging Face models, during `cache populate` |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION` | `outputs = "s3"` |
| `AZURE_STORAGE_ACCOUNT` | `outputs = "azure"`, with a managed identity |
| `AZURE_STORAGE_CONNECTION_STRING` | `outputs = "azure"`, with a connection string |

## Output storage

Images, audio and video are stored as objects and served by the API at
`GET /output/{mode}/{task}/{message_id}/{field}`. `[storage] outputs`
chooses the store:

```toml
[storage]
outputs = "fs"                     # files under the cache's data/outputs

# any S3-compatible service
outputs = "s3"
bucket = "marigold"                # must already exist
endpoint = "http://minio:9000"     # unset means AWS S3
region = "eu-west-2"

# Azure Blob Storage
outputs = "azure"
container = "marigold"             # must already exist
```

For several hosts sharing one store, see [Deployment](deployment.md).

## Resource limits

Every container runs with the limits in `[resources]`, so one service
cannot take the whole machine. An application instance gets 4 GB of
memory, 2 CPUs and 512 processes by default. The worker has no memory
limit by default, because model sizes vary with the host: set
`[resources.worker] memory` below the host's total so a model too large
for the machine fails inside its container, leaving the host running.

The cache container, the worker and application instances run as the
user who runs `marigold`, so the files they write under the cache
belong to that user. Application instances also run hardened: no Linux
capabilities, no privilege escalation, and a read-only root filesystem
with a writable `/tmp`.

## Authentication

Marigold has no authentication of its own. The caller is identified by
an optional `X-User-Id` header, defaulting to `local-user`, and that
header is trusted as received.

On localhost or a private network this needs nothing further. To expose
the API beyond that boundary, put the deployment's own authentication
in front of it -- a reverse proxy, a cloud load balancer, an identity
provider -- and have it set `X-User-Id` for each authenticated caller.
