# Marigold -- Data Contracts

Authoritative reference for DynamoDB table schemas, key formats, component
interfaces, and architectural constraints for the workflow feature. All PK/SK
designs are confirmed. Implement dynawrap items and Terraform table definitions
directly from this document.


---

## Architecture principles

### One model, one execution environment

Each model runs in its own isolated execution environment with its own work
queue. Environments are independent at the infrastructure level: a single
model can fail, time out, or behave erratically without affecting any other.

This boundary produces a natural history per model: reliability, latency,
error rates, and usage patterns are observable at the model level. That history
supports operational decisions -- routing around an unreliable model, retiring
one that underperforms -- and eventually community-visible quality signals.

### models.yaml is the single source of truth

The API routes, the model catalogue, and the Postgres catalogue table are
all derived from models.yaml. The file lives under MARIGOLD_DIR, outside
the repository -- it is not committed, generated, or regenerated at deploy
time. `reconcile_catalogue` syncs the catalogue table against it on every
API startup: add-if-missing, deactivate-if-removed, untouched-if-matched.

Before restarting against a changed models.yaml, validate it:

    docker compose run --rm cache-init python3 -m tools.model_cli validate

This checks the schema and flags duplicate (name, type) entries without
touching HuggingFace or the GPU. It is a manual pre-restart check, not an
automated CI/CD gate -- there is no build step models.yaml passes through.

Adding a model is a YAML change. The catalogue follows on next restart.

### The registry is the handler contract

The @model_spec decorator couples model type, loader, request and response
schemas, and API route at import time. The framework handles routing, input
validation, and output persistence. A handler author implements only _run().

Registering the same ModelType twice raises ValueError at import time, not
at runtime. The constraint is enforced before the process accepts work.

### Model history drives improvement

Every inference call records timing, token counts, and memory usage against
the user and model. Usage records are the substrate for billing, but their
primary value is the history of model behaviour over time. Patterns in that
history -- high latency on a particular model type, elevated error rates,
unusual memory consumption -- identify candidates for replacement or
reconfiguration without requiring manual inspection of individual jobs.

At the workflow level, per-step usage records and outcome fields (accepted,
rejected, partial) allow inspection of where pipelines succeed and where they
fail. That data informs workflow design: which models contribute to rejections,
which steps dominate latency, which prompt strategies produce better acceptance
rates.

### Workflow state is external and durable

Execution state lives in DynamoDB, not in the running process. The workflow
executor reads state at the start of each invocation and writes updated state
before submitting the next step. A process crash at any point loses no state:
the executor re-reads the last committed state on the next trigger and
continues from there.

Intermediate state is available to inspection during execution. A workflow
that crashes mid-run leaves a readable state record showing completed steps,
in-flight steps, per-step outputs, and retry counts. This is a debugging
surface, not a side effect.

## Provider taxonomy

The provider field in models.yaml controls infrastructure generation, cache
builder behaviour, and loader dispatch. It is a dispatch key for the loading
and execution strategy, not a description of model origin.

  huggingface   Weights hosted on HuggingFace Hub. Cache builder downloads
                weights to EFS via the registered loader. ECS task definition
                includes EFS volume mount.

  tools         Callable functions with typed inputs and outputs. No weights,
                no EFS mount, no cache builder step. The ECS task is a
                sandboxed execution environment. Current members: http.

  ollama        Weights served by a local Ollama instance. No EFS mount.
                Handler calls the Ollama HTTP API. Not yet implemented.

  aws-bedrock   Weights managed by AWS Bedrock. No EFS mount. Handler calls
                the Bedrock API via IAM task role. Not yet implemented.

## ID formats

### user_id

Opaque string from the API key auth context. Never generated by Marigold;
always sourced from the authorizer. Must not contain #.

### workflow_id

MD5 hex digest of the canonical runfox spec JSON (sort_keys=True, no
spaces). Generated by runfox Backend.create(). Deterministic: the same
spec always produces the same workflow_id. Content-addressed: submitting
an identical template twice overwrites the same template table record.

### execution_id

{timestamp}-{suffix} where timestamp is UTC in YYYYmmddTHHMMSS format
and suffix is 4 lowercase hex characters. Generated by MarigoldBackend,
which overrides runfox Backend._make_execution_id(). Unique per execution.

Example: 20250318T142301-3af2

### workflow_execution_id

Composite string produced by runfox Backend.workflow_execution_id():

    {workflow_id}#{execution_id}

This is the handle passed between all runfox internal operations and
between Marigold Lambda handlers. DynamoDBStore parses it alongside
user_id (delivered separately) to construct DynamoDB keys.

### op

User-supplied step label from the workflow YAML spec. May contain
arbitrary characters. Never used raw in a DynamoDB key. Always hashed
via MD5 before inclusion in any key component.

    step_id = md5(op.encode()).hexdigest()

The original op string is stored as an attribute on the tasks table
record for display purposes.

### message_id (results table SK)

For workflow step results:

    WORKFLOW#{workflow_id}#{execution_id}#{step_id}#{run_id}

where step_id is md5(op) and run_id is an integer incrementing on each
retry or cascade reset.

For workflow completion records:

    WORKFLOW#{workflow_id}#{execution_id}#COMPLETE#0

## user_id propagation

user_id is never embedded in workflow_execution_id. It travels through
the system as follows:

    API auth context
        -> submission handler
        -> SQS message body (field: user_id)
        -> ECS worker
        -> results table PK: USER#{user_id}
        -> DynamoDB Streams event PK field
        -> router Lambda (strips USER# prefix)
        -> executor Lambda invocation payload (field: user_id)
        -> MarigoldBackend construction
        -> SQS message body for next steps
        -> (repeats from ECS worker)

The router Lambda is the component that extracts user_id from the
Streams event. It reads the PK attribute of the new image, strips the
USER# prefix, and includes user_id explicitly in the executor Lambda
invocation payload.

## SQS message body

One message per dispatched step. Serialised as JSON.

    workflow_execution_id   str   runfox composite key
    user_id                 str   for results table PK and next dispatch
    op                      str   step label (original, not hashed)
    run_id                  int   for stale result detection
    model_type              str   queue routing key
    model_name              str   model identifier; format is provider-specific
                                  (HuggingFace: org/repo, Ollama: name:tag,
                                  tools: arbitrary label)
    prompt_template         str   optional; Python format string
    **inputs                      remaining resolved step input fields

Binary input values (bytes, bytearray) are not permitted. All binary
data must be passed as S3 reference dicts: {"path": str, "mimetype": str}.
The SQSRunner raises NotImplementedError on bytes or bytearray values.

model_type "compute" is not dispatched via SQS. The executor Lambda
handles compute steps locally. SQSRunner raises ValueError for
model_type "compute" so misconfigured compute steps fail loudly.

## Table: workflow templates

Name:       WORKFLOW_TEMPLATE_TABLE (env var)
Purpose:    Stores named runfox YAML specs. One record per unique spec
            per user. Content-addressed: workflow_id is MD5 of spec.

PK:         USER#{user_id}
SK:         TEMPLATE#{workflow_id}

Attributes:
    name            str     human-readable template name
    spec            str     raw YAML string
    created_at      str     ISO 8601 UTC timestamp
    schema_version  str     auto-set by dynawrap DBItem

Access patterns:
    fetch one template:
        get-item on PK=USER#{user_id}, SK=TEMPLATE#{workflow_id}

    list all templates for a user:
        query on PK=USER#{user_id}, SK begins_with "TEMPLATE#"

dynawrap item:

    class WorkflowTemplate(DBItem, BaseModel):
        pk_pattern = "USER#{user_id}"
        sk_pattern = "TEMPLATE#{workflow_id}"

        user_id:        str
        workflow_id:    str
        name:           str
        spec:           str
        created_at:     str

## Table: workflow state

Name:       WORKFLOW_STATE_TABLE (env var)
Purpose:    Full execution state for one workflow run. One record per
            execution. Written by the executor Lambda after each
            advance() call. Read by the executor Lambda on every step
            result and by the status API endpoints.

PK:         USER#{user_id}
SK:         WORKFLOW#{workflow_id}#EXEC#{execution_id}

Attributes:
    workflow_execution_id   str     runfox composite key; stored for
                                    convenience in executor Lambda
    runfox_state            str     JSON of WorkflowRecord.to_dict();
                                    opaque to all layers except
                                    DynamoDBStore and the executor Lambda
    status                  str     pending | in_progress | complete |
                                    halted | cancelled
    outcome                 str     JSON of resolved workflow outputs;
                                    null until terminal
    created_at              str     ISO 8601 UTC timestamp
    updated_at              str     ISO 8601 UTC timestamp
    schema_version          str     auto-set by dynawrap DBItem

Access patterns:
    fetch one execution:
        get-item on PK=USER#{user_id},
        SK=WORKFLOW#{workflow_id}#EXEC#{execution_id}

    list all executions of a template for a user:
        query on PK=USER#{user_id},
        SK begins_with "WORKFLOW#{workflow_id}#EXEC#"
        results are time-ordered (SK is lexicographically sortable)

    list all executions for a user across all templates:
        not supported by this key design; not required by the API

dynawrap item:

    class WorkflowExecution(DBItem, BaseModel):
        pk_pattern = "USER#{user_id}"
        sk_pattern = "WORKFLOW#{workflow_id}#EXEC#{execution_id}"

        user_id:                str
        workflow_id:            str
        execution_id:           str
        workflow_execution_id:  str
        runfox_state:           str
        status:                 str
        outcome:                str | None = None
        created_at:             str
        updated_at:             str

DynamoDBStore.load(workflow_execution_id, user_id) parses
workflow_execution_id to extract workflow_id and execution_id, then
constructs PK and SK to perform the get-item.

DynamoDBStore.write(record, user_id) performs the same parse and
constructs the key before put-item.

## Table: workflow steps

Name:       WORKFLOW_STEPS_TABLE (env var)
Purpose:    Observability record for each dispatched step, including
            retries. Written by SQSRunner.dispatch() on every dispatch.
            Updated in place when the step result arrives.
            Read by the step detail API endpoints.

            A retry is a new record (run_id increments, new SK). The
            step detail endpoint returns all runs for a step ordered
            by run_id.

            Not the authoritative step state -- that lives in
            WorkflowRecord.steps inside runfox_state on the workflow
            state table. The steps table is the observability record;
            the state table is the execution record.

PK:         USER#{user_id}#WORKFLOW#{workflow_id}
SK:         EXEC#{execution_id}#STEP#{step_id}#RUN#{run_id}

where step_id = md5(op)

Attributes:
    user_id         str     for record attribution
    workflow_id     str
    execution_id    str
    op              str     original user-supplied step label
    step_id         str     md5(op)
    run_id          int
    model_type      str
    model_name      str
    status          str     dispatched | complete | failed
    submitted_at    str     ISO 8601 UTC timestamp
    completed_at    str     ISO 8601 UTC; null until complete
    output          str     JSON of step output dict; null until complete
    schema_version  str     auto-set by dynawrap DBItem

TTL: 30 days from submitted_at. Keeps the table bounded without
explicit cleanup.

Access patterns:
    all steps for an execution:
        query on PK=USER#{user_id}#WORKFLOW#{workflow_id},
        SK begins_with "EXEC#{execution_id}#"

    all runs for a specific step:
        query on PK=USER#{user_id}#WORKFLOW#{workflow_id},
        SK begins_with "EXEC#{execution_id}#STEP#{step_id}#"

    one specific run:
        get-item on full PK + SK

    steps not yet dispatched (status READY, dependencies unmet):
        no steps table record exists; the step detail endpoint falls
        back to WorkflowRecord.steps in runfox_state on the workflow
        state table in this case

dynawrap item:

    class WorkflowStep(DBItem, BaseModel):
        pk_pattern = "USER#{user_id}#WORKFLOW#{workflow_id}"
        sk_pattern = "EXEC#{execution_id}#STEP#{step_id}#RUN#{run_id}"

        user_id:        str
        workflow_id:    str
        execution_id:   str
        op:             str
        step_id:        str
        run_id:         int
        model_type:     str
        model_name:     str
        status:         str
        submitted_at:   str
        completed_at:   str | None = None
        output:         str | None = None

## Table: results (existing)

Name:       RESULTS_TABLE (env var)
Purpose:    Inference results for all jobs: direct API requests and
            workflow steps. Written by ECS workers. Read by the polling
            API for direct requests and by DynamoDB Streams for workflow
            step routing.

            Direct API results use the API# message_id prefix.
            Workflow step results use the WORKFLOW# message_id prefix.
            The router Lambda filters on prefix to determine handling.

PK:         USER#{user_id}
SK:         API#{apigw_request_id}          (direct API jobs)
            WORKFLOW#{workflow_id}#...      (workflow step results)

Attributes (existing):
    sts     str     "queued" | "complete"
    rsp     str     JSON of inference result

DynamoDB Streams on this table drive the workflow routing path.
The router Lambda subscribes to the stream and dispatches on message_id
prefix. See DynamoDB Streams routing section below.


### message_id formats for the results table SK

Direct API requests:

    API#{md5(request_body_utf8)}

The MD5 of the raw request body provides request deduplication: identical
requests from any source hit the cache without spawning a new task. The
API Gateway requestId is logged alongside the MD5 at submission time for
trace correlation in CloudWatch. The deduplication property is intentional
and load-bearing: it prevents duplicate task launches under retry storms
or client bugs.

Workflow step results use the WORKFLOW# prefix format defined above.
BATCH# and SCHEDULE# prefixes are reserved.

## DynamoDB Streams routing (message_id prefix convention)

The router Lambda dispatches on message_id prefix. Defined prefixes:

  API#      direct HTTP request via API Gateway -- no further action
  WORKFLOW# workflow step result -- invoke workflow_executor Lambda
  BATCH#    reserved, deferred
  SCHEDULE# reserved, deferred

The # character must be absent from all component values (request IDs,
workflow IDs, execution IDs, op names) to function correctly as a
delimiter.

## ECS worker output contract

ECS workers write inference results to the results table using the
WORKFLOW# message_id prefix for workflow steps and the API# prefix for
direct requests. The router Lambda receives the Streams event and
invokes the workflow executor Lambda for WORKFLOW# records.

The output dict top-level keys must match the field names referenced by
downstream step var expressions.

Example: if a downstream step declares:
    text: {"var": "steps.classify.output.category"}

then the classify step output dict must contain:
    {"category": "..."}

Binary outputs are written to S3 and referenced in the output dict as:
    {"path": "outputs/{model_type}/{message_id}/{field}", "mimetype": "..."}

Downstream steps receive the S3 reference dict as their input value.
Raw bytes are not valid step output values.

## Dummy model contract

model_type: dummy
Handled by a Lambda, not an ECS task. No model weights required.
Added to QUEUE_MAP under md5("dummy") -> QUEUE_URL_DUMMY.

    model_name: echo
        Returns all non-control input fields as output fields unchanged.
        Control fields (model_type, model_name, prompt_template) are
        consumed by SQSRunner before dispatch and do not appear in output.

    model_name: true
        Returns {"result": true}.

    model_name: false
        Returns {"result": false}.

Indistinguishable from a real model step in the routing path.
Used for branch condition testing, input resolver validation, and
end-to-end workflow testing on live AWS infrastructure without ECS
cluster or model weights.

## Http tool contract

model_type: http
provider:   tools
Handled by an ECS task. No model weights. No EFS mount.

Request fields:
    url       str             target URL
    method    str             HTTP method (default: GET)
    headers   dict | null     optional request headers
    body      dict | null     optional request body (non-GET only)
    timeout   int             seconds before timeout (default: 30)

Response fields:
    status    int             HTTP status code
    body      dict            parsed JSON response body
    headers   dict            response headers

Only application/json responses are supported. The handler raises
ValueError on any other content type. Binary and HTML responses
are explicitly out of scope.

The http step executes in a sandboxed ECS container with network
access scoped by the task security group. External calls specified
in a workflow YAML are executed in the container, not in the
executor Lambda. This is a security boundary: user-specified
external calls must not execute in the coordinator process.

## Table: usage

Name:       DYNAMODB_USAGE_TABLE (env var)
Purpose:    Per-request inference usage records. Written once per completed
            inference request. Never updated. Supports per-user, per-period
            usage queries for billing and analytics.

PK:         METRIC#RAW#USER#{user_id}
SK:         DATE#{recorded_at}#OP#{operation}

where recorded_at is UTC in YYYYmmddTHHMMSSZ format and operation is
{model_type}/{model_name}.

Attributes:
    user_id         str     authenticated caller
    recorded_at     str     UTC timestamp of the write
    operation       str     {model_type}/{model_name}
    duration        float   total process duration in seconds
    inference       float   model inference duration in seconds
    input_tokens    int     input token count (0 for non-text models)
    output_tokens   int     output token count (0 for non-text models)
    memory_usage    int     peak process memory in KB

Access patterns:
    all records for a user:
        query on PK=METRIC#RAW#USER#{user_id}

    records for a user within a date range:
        query on PK=METRIC#RAW#USER#{user_id},
        SK between DATE#{start} and DATE#{end}

    records for a user for a specific operation:
        query on PK=METRIC#RAW#USER#{user_id},
        SK begins_with DATE#{date}#OP#{operation}

dynawrap item: UsageItem in shared/db_models.py
